# Contributing Guidelines

This document defines the project standards for issues, pull requests, and commit messages.

The goal is to keep the workflow clear, lightweight, and GitHub-native. Issues describe what needs to be done, pull requests describe what changed, and commits describe the individual steps that produced the change.

## Recommended end-to-end flow

Example for a task:

1. Navigate to the project page and create a new issue in the in the "Todo" column.
2. Do not include the label here, as the issue template will add it automatically.
3. Select the corresponding issue template and fill in the details.
4. In the sidebar create a new branch from the issue. Use the autogenerated branch name.
5. Check it out locally and implement the change.
6. Push your commits using the Conventional Commits format.
7. Navigate to the branch page and create a pull request from the branch. Use the discussed title and select the PR template.
8. Ensure the Workflow check passes and merge the pull request.

## Guiding principle

Keep the workflow simple.

Issues should make the work clear.
Pull requests should make the change reviewable.
Commits should make the history understandable.

## Issues

Issues are the source of truth for planned work, bugs, research, decisions, documentation, and technical debt.

Every meaningful piece of work should have an issue before implementation starts.

Issues should be created from the project page, not the repository's.

### Issue labels

Use one primary label per issue to describe the kind of work.

| Label           | Use for                                                    |
| --------------- | ---------------------------------------------------------- |
| `feature`       | New product functionality or larger user-facing capability |
| `bug`           | Broken or incorrect behavior                               |
| `task`          | Concrete implementation or maintenance work                |
| `spike`         | Research, investigation, or unknowns                       |
| `documentation` | README, docs, setup notes, or internal explanations        |

### Issue templates

Use the matching issue template when creating a new issue:

| Template      | Use when                                          |
| ------------- | ------------------------------------------------- |
| Feature       | Something new should exist in the product         |
| Bug           | Something is broken                               |
| Task          | A concrete piece of implementation work is needed |
| Spike         | Research is needed before deciding or building    |
| Documentation | Documentation should be added or updated          |

### Issue naming

Use this format:

```text
<Type>: <Verb in imperative> <short description>
```

Examples:

```text
Feature: Add court booking calendar
Bug: Disallow overlapping court reservations
Task: Add tenant_id to bookings table
Spike: Research branch naming convention
Documentation: Document local development setup
```

The issue title should be understandable on its own.

## Branches

Branches should be generated from the issue page.
Use GitHub's autogenerated branch name, which includes the issue number and type

## Pull Requests

Pull requests are the reviewable unit of change.

### Pull request naming

Use a short, human-readable title that describes what changed.

Examples:

```text
Add issue templates
Add pull request template
Document GitHub workflow
Add tenant resolver middleware
Prevent overlapping bookings
Configure authentication
```

Avoid putting the issue type in the PR title.

Do not use:

```text
Task: Add issue templates
Bug: Prevent overlapping bookings
PAD-7 add stuff
fix things
WIP
```

The issue already contains the type. The PR title should describe the change.

### Pull request template

Every pull request should use the project PR template. Feel free to add more details to the template body, but the title and body should at least include the autogenerated content.

### Pull request size

Prefer small pull requests that close one issue.

A PR can contain multiple commits, but it should usually represent one coherent change.

If a PR becomes hard to describe clearly, split it.

## Commits

Use lightweight Conventional Commits.

### Commit format

Use this format:

```text
<type><(scope)>: <verb in imperative> <short description>
```

Examples:

```text
feat: add tenant model
fix: prevent overlapping bookings
docs: document GitHub workflow
chore: add issue templates
refactor: extract tenant resolver
test: add tenant isolation tests
style: format issue templates
```

With scope:

```text
feat(booking): add court booking calendar
fix(auth): handle expired login session
docs(github): document issue workflow
refactor(tenant): extract tenant resolver middleware
test(booking): add overlap validation tests
```

### Commit types

Use these commit types:

| Type       | Use for                                    |
| ---------- | ------------------------------------------ |
| `feat`     | New feature or product behavior            |
| `fix`      | Bug fix                                    |
| `docs`     | Documentation-only change                  |
| `chore`    | Tooling, config, templates, maintenance    |
| `refactor` | Code restructuring without behavior change |
| `test`     | Adding or updating tests                   |
| `style`    | Formatting-only changes                    |

### Commit message style

Use imperative language.

Good:

```text
feat: add booking calendar
fix: reject overlapping bookings
docs: document pull request workflow
chore: add issue templates
```

Avoid:

```text
added booking calendar
fixed overlap bug
changes
update stuff
WIP
```
